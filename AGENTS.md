# Repository Guidelines

## Project Structure

pgsketch is a pnpm workspace (`pnpm-lock.yaml`) with two packages. The full design lives in `docs/pgsketch — Build Plan (0.1.0).md`.

- `packages/core`: pure TypeScript (schema model, introspection, diff, SQL rendering). No Electron, React or `pg` dependency. Tests live in `packages/core/test/`.
- `apps/desktop`: the Electron app, built with electron-vite. Main process in `src/main/`, preload in `src/preload/`, React renderer in `src/renderer/src/`.

## Build, Test, and Development Commands

Run these from the repo root unless noted:

- `pnpm install` installs dependencies from `pnpm-lock.yaml`.
- `pnpm lint` runs ESLint and a Prettier check.
- `pnpm format` runs Prettier on the whole repo.
- `pnpm typecheck` runs TypeScript type checking in every package.
- `pnpm test` runs unit and component tests (it skips the Docker-based DB tests).
- `pnpm --filter @pgsketch/core test:db` runs the Postgres tests in Docker. Set `PG_VERSION` (14-18, default 16) to pick the version.
- `pnpm --filter @pgsketch/desktop dev` starts the Electron app with hot reload.
- `pnpm --filter @pgsketch/desktop build` typechecks and builds the app.
- `pnpm --filter @pgsketch/desktop start` previews the production build.
- `pnpm --filter @pgsketch/desktop test:e2e` builds the app and runs the Playwright tests. It needs a display (`xvfb-run` in CI).
- To add a shadcn component, run `pnpm dlx shadcn@4.22.1 add <component>` from `apps/desktop`.

## Coding Style & Naming Conventions

- Write TypeScript and TSX with strict compiler settings.
- In the desktop renderer, use the `@/*` path alias (it points at `apps/desktop/src/renderer/src`). `packages/core` has no alias.
- Try to avoid `any` or `unknown` types as much as possible. Keep **EVERYTHING** type-safe.
- Components use PascalCase filenames and exports, for example `ThemePanel.tsx`; hooks use `use-*` naming, for example `use-mobile.ts`; utility modules use short lowercase names such as `lib.ts`. Files generated by shadcn (`components/ui/*`, `lib/utils.ts`) keep their generated names.
- Keep screens thin and put domain UI in its own folder under the renderer (`screens/`, `canvas/`, `editors/`, `chrome/`, `sql/`, `stores/`, as laid out in the build plan); shared, domain-agnostic UI lives in `components/`.
- Never make a single file too long. Do code splitting with easily manageable/understandable file structure.
- Always follow DRY strategy for everything. Whether it's a type/interface declaration or even a simple utility function. Never write same logic in multiple places.
- Keep everything easily extensible. If any css color is needs to be used that isn't available in `apps/desktop/src/renderer/src/assets/main.css` already, never use tailwind arbitrary values. always declare them as variables in that file and use those variables in the classnames.
- For any frontend related task, use shadcn/ui components as much as possible.
- When asked to move a component's logic to a custom hook, determine if this hook is component-specific or will be reused across multiple components. For component-specific hooks, move the component jsx to it's own directory first and then place the custom hook inside that directory. So `components/Example.tsx` should become `components/Example/index.tsx` and the path for the custom hook should be `components/Example/use-custom-hook.ts`. For reusuable hooks, place it in a `hooks/` directory in the renderer (`apps/desktop/src/renderer/src/hooks/`).
- All SQL goes through `quoteIdent` and `quoteLiteral` (`packages/core/src/sql/quote.ts`). Never build SQL by concatenating names or values.

## Testing Guidelines

- Unit and component tests use Vitest (plus React Testing Library and jsdom in the desktop app). Desktop tests are colocated with the code as `*.test.ts` or `*.test.tsx`. Core tests live in `packages/core/test/`.
- Tests that need a real Postgres use the Testcontainers helper in `packages/core/test/pg.ts` and are named `*.db.test.ts`. They run with `test:db`, not `test`.
- End-to-end tests use Playwright's Electron support and live in `apps/desktop/e2e/`.
- CI runs lint, typecheck and tests on every push, with the DB tests on Postgres 14-18 and the E2E test under xvfb.
- Each build-plan phase ends with a passing test. Keep the phase's **Status** column in the build plan current: `todo`, `working` while building, `done` when complete.

## Commit & Pull Request Guidelines

Keep commits atomic:

- commit only the files you touched and list each path explicitly. For tracked files run `git commit -m "<scoped message>" -- path/to/file1 path/to/file2`. For brand-new files, use the one-liner `git restore --staged :/ && git add "path/to/file1" "path/to/file2" && git commit -m "<scoped message>" -- path/to/file1 path/to/file2`.
- Always check the changed files by `git status` before committing. Never commit files from the thread context.
- Never change any file content before committing.
- PRs should explain user-visible impact, list schema or config changes, and link related issues. It also should include a short summary, validation steps, and linked issues when relevant. Note any schema, environment, or migration impact explicitly.
- Do not commit any changes unless you're asked to. Do not push unless you're asked to.
- Commit directly to `main`. Do not create a new branch for commits unless explicitly asked to.
- Pull request comments should always be in casual tone, never include unnecessary descriptions or details, and should be include proper file references.

## Security & Configuration Tips

- Do not commit secrets, local environment files and generated output such as `out/` and `dist/`. The `build/` directory holds app icons and other build resources, so it is tracked.
- Passwords never reach the renderer: saved connections are opened by ID in the main process, and all IPC input is validated with zod in the main process.
- Do not move from one phase/task to another unless i ask you to specifically.
- Add all your decisions in a `DECISIONS.md` file in the `docs/` directory. If the file doesn't exist, create it. Add a new section for each decision with a title, date & time, and description of the decision and its rationale. The build plan's Decisions table holds the settled 0.1.0 decisions; `docs/DECISIONS.md` holds the ones made while building.

## Behavioral Guidelines

### 1. Think Before Coding

**Don't assume. Don't hide confusion. Surface tradeoffs.**

Before implementing:

- State your assumptions explicitly. If uncertain, ask.
- If multiple interpretations exist, present them - don't pick silently.
- If a simpler approach exists, say so. Push back when warranted.
- If something is unclear, stop. Name what's confusing. Ask.

### 2. Simplicity First

**Minimum code that solves the problem. Nothing speculative.**

- No features beyond what was asked.
- No abstractions for single-use code.
- No "flexibility" or "configurability" that wasn't requested.
- No error handling for impossible scenarios.
- If you write 200 lines and it could be 50, rewrite it.

Ask yourself: "Would a senior engineer say this is overcomplicated?" If yes, simplify.

### 3. Surgical Changes

**Touch only what you must. Clean up only your own mess.**

When editing existing code:

- Don't "improve" adjacent code, comments, or formatting.
- Don't refactor things that aren't broken.
- Match existing style, even if you'd do it differently.
- If you notice unrelated dead code, mention it - don't delete it.

When your changes create orphans:

- Remove imports/variables/functions that YOUR changes made unused.
- Don't remove pre-existing dead code unless asked.

The test: Every changed line should trace directly to the user's request.

### 4. Goal-Driven Execution

**Define success criteria. Loop until verified.**

Transform tasks into verifiable goals:

- "Add validation" → "Write tests for invalid inputs, then make them pass"
- "Fix the bug" → "Write a test that reproduces it, then make it pass"
- "Refactor X" → "Ensure tests pass before and after"

For multi-step tasks, state a brief plan:

```
1. [Step] → verify: [check]
2. [Step] → verify: [check]
3. [Step] → verify: [check]
```

Strong success criteria let you loop independently. Weak criteria ("make it work") require constant clarification.

---

**These guidelines are working if:** fewer unnecessary changes in diffs, fewer rewrites due to overcomplication, and clarifying questions come before implementation rather than after mistakes.
